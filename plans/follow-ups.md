# Follow-ups

Bugs noticed outside the task at hand, each with a repro so it can be re-checked later. Written by `/bs-loop` reviewers and by any agent session. Open items only: `/bs-plan follow-ups` re-probes them, groups them by root cause, and moves each into a plan (as a fix task or a deferred row), deleting it here.

Each entry names its root cause (the mechanism that produces it, not the path that exposed it) and its route: the open plan whose scope covers that root, or `unrouted`. Entries with the same root sit together. A defect with the same root as the task being fixed is part of that task and never lands here (`/bs-loop` **Follow-ups**).

- **Checker:** A non-constant shift with an untyped left operand assigned to a non-integer type is accepted, though Go types the shifted operand from the context and rejects it. Root: `untyped-shift-context` (`src/typechecker/assignability.js:_retypeUntypedShift` retypes the shift tree only for integer targets and never reports a non-integer one). Repro: `var s uint = 1; var x float64 = 1 << s` (also `var x T = 1 << s` with `T ~int | ~float64`) → got accepted on `js`, `internal compiler error: Unsupported WASM instruction opcode: 'f64.ge_u'` on `wasm`, want `invalid operation: shifted operand 1 (type float64) must be integer`. (feat/checker-go-rules-phase-16, checker-go-rules Phase 16, Out of Scope) → checker-go-rules
- **Checker:** Comparing a type-parameter value with an interface value skips the assignability check, so Go's rejections are accepted and `wasm` emits an invalid module. Root: `type-param-value` (`src/typechecker/assignability.js:_matchTypeParamOperands` leaves interface operands to the comparison rules, which have no type-parameter-to-interface assignability yet; `_typeBinaryOperands` returns early for a Go `any` operand). Repro: `func f[T ~int | ~float64](a T, b I) bool { return a < b }` with `type I interface{ M() }`, and `func g[T any](a T, b any) bool { return a == b }` → got accepted on `js` and an invalid WebAssembly module on `wasm`, want `invalid operation: a < b (mismatched types T and I)` and `invalid operation: a == b (incomparable types in type set)`. (feat/checker-go-rules-phase-16, checker-go-rules Phase 16, Out of Scope) → checker-go-rules
- **Checker:** An `if` or `for` condition of type-parameter type is rejected even when every term of its type set is a boolean. Root: `type-param-value` (`src/typechecker/statements.js` condition checks test `isBool` on the operand type directly, with no type-set check for a `typeParam`). Repro: `func F[T ~bool](a T) int { if !a { return 1 }; return 2 }` (also `for !a`, `if a`) → got `If condition must be bool`, want accepted and `F(false)` returns `1`. (PR #248, checker-go-rules Phase 16, Out of Scope) → checker-go-rules
- **JS backend:** Shifting an `int` by 32 or more in a `js` package uses JavaScript's 32-bit `<<`, so the result is wrong although `int` holds integers up to 2⁵³ there. Root: `js-int-shift` (`src/backend/js/expressions.js` emits a native `<<` for `int`; only 64-bit types go through `__shl64`). Repro: `func G(s uint) { one := 1; fmt.Println(one << s) }; G(40)` → got `256`, want `1099511627776`. (feat/checker-go-rules-phase-16, checker-go-rules Phase 16, Out of Scope) → unrouted
- **JS backend:** A compound shift on a map element by a 64-bit or type-parameter count skips the count conversion and the negative-count check that other shift targets get. Root: `js-compound-shift-count` (`src/backend/js/statements.js:_genAssignStmt` map-index compound path does not use `_compoundShiftCount`). Repro: `m := map[string]int{"a": 1}; var s uint64 = 10; m["a"] <<= s` → got `TypeError: Cannot mix BigInt and other types` on `js`/`both`, want `m["a"] == 1024`; with `var s int = -1` want panic `negative shift amount`. (PR #248, checker-go-rules Phase 16, Out of Scope) → checker-go-rules
- **Checker:** Untyped float and complex constants are not checked for representability against a complex type parameter's terms or as a shifted operand. Root: `const-representability` (`src/typechecker/assignability.js:_untypedFitsTerm` skips the overflow check for complex targets; `_isShiftableUntyped` lets an imaginary constant through because it carries no tracked value). Repro: `func F[T ~complex64](a T) T { return a + 1e40 }` and `func G[T ~uint](s T) { _ = 1i << s }` → got accepted on all targets, want `cannot convert 1e40 (untyped float constant 1e+40) to type T` and `invalid operation: shifted operand 1i (untyped complex constant) must be integer`. (PR #248, checker-go-rules Phase 16, Out of Scope) → checker-operand-rules
- **WASM backend:** A generic defined type over a generic struct that embeds another generic struct fails to compile on `wasm`. Root: `wasm-defined-generic-embed` (`src/backend/wasm/monomorph.js` / `src/backend/wasm/module-emitter.js` do not map the embedded generic field on the monomorphised instance). Repro: `type Inner[A any] struct{ Y A }; type S[A any] struct{ Inner[A]; X A }; type W[B any] S[B]; w := W[int]{Inner: Inner[int]{Y: 11}, X: 22}; fmt.Println(w.Y, w.X, w.Inner.Y)` → got `internal compiler error: Unknown field 'Inner' on struct 'W$int'` on `wasm`, want `11 22 11`. (PR #249, checker-go-rules Phase 19, Out of Scope) → wasm-struct-types
- **Checker:** Methods declared on a generic type whose underlying type is not a struct or interface are lost when it is instantiated. Root: `generic-nonstruct-methods` (`src/typechecker/resolve.js:instantiateGenericWithArgs` sets `named.methods = instantiated.methods`, which is `undefined` for non-struct underlying types, so `_syncInstanceMethods` returns early). Repro: `type W[T any] []T; func (w W[T]) Len() int { return len(w) }; fmt.Println(W[int]{1, 2, 3}.Len())` → got `W[int] has no field or method 'Len'` on all targets, want `3`. (PR #249, checker-go-rules Phase 19, Out of Scope) → unrouted
- **Backends:** Converting a struct value to its own type returns the same object instead of a copy, so writes through the result change the source. Root: `struct-identity-conversion-copy` (`src/backend/js/expressions.js:_genStructClassConversion` returns `null` for a same-type conversion and the caller emits the argument unchanged; wasm has the same aliasing for a generic instance). Repro: `type T struct{ X int }; src := T{X: 1}; dst := T(src); dst.X = 2; fmt.Println(src.X, dst.X)` → got `2 2` on `js` (and on `wasm` for `type T[A any] struct{ X int }` with `T[int]`), want `1 2`. (PR #249, checker-go-rules Phase 19, Out of Scope) → unrouted
- **JS backend:** `clear`, `len` and `copy` on a type-parameter operand pick their JavaScript form from the operand's static type, so a type parameter is lowered as a slice: `clear` on a map (also with `M ~map[K]V`) throws, `clear` on `S ~[]int` fills with a wrong zero, `len` of a `~*[3]int` term reads `.length` of the pointer, and `copy` from a `~[]byte | ~string` source copies zeros. Root: `js-typeparam-builtin` (`src/backend/js/expressions.js:_genBuiltinClear`, `_genBuiltinLen`, `BUILTIN_GEN.copy` read `arg._type` without resolving the type argument). Repro: `func C[M ~map[string]int](m M) { clear(m) }; C(map[string]int{"a": 1})` → got `m?.fill is not a function` (js/both), want no output and `len(m) == 0` (wasm correct); `func L[T ~[]int | ~*[3]int](v T) int { return len(v) }; a := [3]int{}; L(&a)` → got `1`, want `3`. (feat/checker-go-rules-phase-17, checker-go-rules Phase 17, Out of Scope) → unrouted
