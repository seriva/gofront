# v1.9.1 Review Follow-ups (2026-11-12) — Design Plan

**Version:** v1.9.1  
**Status:** In Progress  
**Base branch:** main  
**Related:** [`follow-ups-2026-11-11-plan.md`](follow-ups-2026-11-11-plan.md) (origin of every ledger entry, PRs #180–#183, merged into main as #184), [`follow-ups-2026-11-10-plan.md`](follow-ups-2026-11-10-plan.md)  
**Release note:** Structs that embed an interface (`struct{ error }`) now get its methods, explicit func type arguments (`f[func(int)]()`) parse, and WebAssembly builds no longer produce invalid modules for range assignments into an `any` or for a range-over-func loop nested in a `range` loop. Named array and slice types keep their identity in an `any` on WebAssembly, `complex64` arithmetic and typed constants keep float32 precision in JavaScript, and a field or method promoted from two embedded types at the same depth is now reported as an ambiguous selector, as in Go. A method promoted from an embedded type now wins over a same-named field embedded deeper, `append` of untyped constants to `[]complex128` works in JavaScript, a range assignment into an interface keeps a named type's methods in JavaScript, arrays, slices and maps keep their element types in an `any` on WebAssembly, `fmt` prints a slice that generic code boxes into an `any`, and WebAssembly builds accept untyped constants where a complex value is stored through a pointer, switched on or passed to a deferred call. Deferred calls with variadic parameters, `nil` arguments or untyped constants for generic or defined-type parameters work on WebAssembly and with spread arguments in JavaScript, a range assignment into a slice element, field or pointer works on WebAssembly and a range-over-func assignment into an interface keeps its type in JavaScript, a nil defined slice asserted out of an `any` is nil in JavaScript, `fmt` prints an array that generic code boxes into an `any`, and comparing complex values in JavaScript evaluates each operand once. A comparison result (`x == 1`) is accepted where a defined bool type is expected, a rune literal has type `rune`, deferred non-constant untyped arguments take the parameter's type, `fmt` prints maps and arrays with `bool` or small-integer keys and elements that are boxed into an `any`, and a range-over-func assignment into a slice element, field or pointer target works in JavaScript. `&&` and `||` of defined bool values keep their type, an array length, index or `make` size that is not an integer constant is a compile error instead of a wrong program, a range-over-func assignment is checked against its target's type, `fmt` names maps with `bool` or small-integer keys and func values in an `any`, and generic code that boxes several maps or arrays into an `any` in JavaScript keeps each one's own type.

## Approach

### 1. Architecture & Design Decisions

- **`J06` (Task 1.1):** add `T.RBRACKET` to the `inTypeExpr` terminators in `parseReturnType`. `a[func(int) int{…}]` style index expressions are unaffected because `tryParseTypeLiteralArgs` already restores position on failure.
- **`J03` (Tasks 1.2–1.3):** promoted fields get the same depth model as promoted methods (11-11 Task 2.1/2.2): `_offerEmbedMethods` records each promoted field's depth alongside the method candidates in one name → candidate map, so a field and a method (or two fields) at the same minimal depth make the name ambiguous, and a shallower one wins. `_fieldTypeStruct` checks ambiguity before returning a promoted field; a field declared on the struct itself always wins. Composite literal keys (`C{A: A{}}`) and the embedded field names themselves (`c.A`, depth 0) are unaffected. Field lookups in both backends already go through the typechecker's resolved path, so no backend change is expected; the tests pin all targets.
- **`J02` (Phase 2):** an embedded interface `I` contributes every method of `I`'s method set at depth 1, with `viaPtr: false` (value method set), through the same candidate map (ambiguity and shadowing rules unchanged).
  - Typechecker (Task 2.1): `_offerEmbedMethods` handles `base.kind === "interface"` (named or literal, including `error`), offering its `methods`.
  - JS (Task 2.2): `computeEmbeddedStubs` emits a forwarding stub for each interface method (`m(...a) { return this.<Field>.m(...a); }`), so `typeof v.M === "function"` holds and a nil embedded interface throws the nil-dereference panic through `__nilcall` in strict packages.
  - WASM (Task 2.3): `_findPromotedMethod` treats an interface-typed embed field as a candidate whose call loads the field and dispatches through the existing interface call path (the field holds an `anyref`), and direct calls `S{T{}}.M()` lower to the same field load + interface call.
- **`J04` (Task 2.4):** when `cand.embedPath` contains a pointer step and the target method has a value receiver, emit `ref.is_null` on that step's result and call the nil-dereference panic helper before `emitCloneStruct`. Same message as `_emitNilPtrCandidate`.
- **`J05` (Task 3.1):** a named (defined) slice or array type stored in an `any` keeps its identity: named slices always use `getTaggedSliceType` (tag per `goTypeKey`), named arrays get an interface box (`getIfaceBoxType`, as named maps/funcs with methods already do). Type assertions, type switches, `any_eq`/`any_hash` (11-11 Task 3.1/3.2 array arms) and `_dynamicTypeNames` use the same box, so `k.([2]int)` misses and `k.(A)` hits. Unnamed arrays/slices keep their current representation (no change to hot paths that never reach an `any`).
- **`J07` (Task 3.2):** probe first: compare the map/slice type the monomorphised `mk[func()]` registers with the assertion target's (`goTypeKey` and wasm type). Fix at the source of the divergence (substitution of `V` before `getMapType`/`getSliceType` in `src/backend/wasm/monomorph.js`, or closure wasm type normalisation); record the root cause in the commit body.
- **`J08` (Task 3.3):** `_dynamicTypeNames` adds `mod.arrayTypes` entries keyed by their Go type (record `goType` on `arrInfo`), and slices whose element is a func/interface-like type get a tagged slice when stored in an `any` (so `[]func()` and `[]any` are distinguishable by `ref.test`). Only names are affected for arrays; for `[]func()` the tag also fixes `w.([]any)` falsely succeeding (assert in the test).
- **`J01` (Task 4.1):** `_emitRangeAssignStore` takes the target's Go type; when it is an interface, `emitValue` is followed by the existing interface boxing of the element Go type (`_emitBoxValue` / `emitToAny`, as assignment statements do). Applies to all range kinds (int, slice, array, string, map, chan-free).
- **`J09` (Task 4.2):** wherever the yield-closure environment captures a variable, the stored value is converted from the local's wasm type to the env field's wasm type (`i64.extend_i32_s` for an i32 index local of a Go `int`). Prefer fixing at the capture site over widening range index locals to i64 (would touch hot loop codegen; `test/perf/zero-alloc.js`).
- **`J10` (Task 4.3):** the strict interface-call path uses `this._genCallArgs(expr)`.
- **`J11` (Task 4.4):** (a) the typechecker tags uses of a typed `complex64` constant (`Ident`/`SelectorExpr` whose `_const` is complex and whose type is `complex64`) with `_c64Const`, and `complexConstParts` already folds them (11-11 Task 4.4); (b) untyped complex operands of a `complex64` binary expression are tagged `_c64Const`; (c) `_genComplexBinary` wraps `+ - * /` result components in `Math.fround` when `expr._type` is `complex64` (via a `__c64` helper for `__cmul`/`__cdiv` results).

- **`K01` (Tasks 5.1–5.2):** a method promoted at a shallower depth than a same-named field wins (Go's depth rule), in the same candidate model as 1.2/1.3.
  - Typechecker (5.1): selector, call and method-value resolution consult the depth model before the flattened field map, so `C{}.M()` and `c.M` resolve to `B.M`.
  - JS (5.2): the class emits the stub for the winning method and does not define the deeper field as an own property of the outer class (the field stays reachable as `c.A.In.M`), so `i.M()` through an interface calls the method.
- **`K03` (Tasks 6.1–6.3):** an `any` boxes values by Go type, not by wasm type.
  - 6.1 arrays: every array stored in an `any` gets an interface box keyed by `goTypeKey` (named arrays already do, 3.1); type assertion, type switch, `any_eq`/`any_hash` and `_dynamicTypeNames` use the box.
  - 6.2 slices: slices whose wasm element type is shared by several Go types (`int`, `int64`, `uint`, `uint64`, `uintptr` are i64) join `TAGGED_SLICE_ELEMS`, so `getTaggedSliceType` tags them per Go type in an `any`; `test/perf/zero-alloc.js` must stay unchanged (tagging happens on boxing into an `any`, not in loops).
  - 6.3 maps: a map stored in an `any` whose key or value Go type shares a wasm type with another Go type is boxed by `goTypeKey` (named maps already are).
- **`K04` (Task 6.4):** pin at task start with a probe. Give the interface box of a composite literal whose static type contains a type parameter the same treatment `map[string]V` gets: JS fmt metadata from the instantiated type on every call, and the WASM monomorph substitutes `V` before the box/name is recorded. Record the root cause in the commit body.
- **`K05` (Task 5.3):** `BUILTIN_CHECK.append` calls `_tagComplexConst` (and `_tagFloat32Const`, already correct for `float32`) for every non-spread argument against the slice's element type; JS codegen already consumes `_asComplex` / `_c64Const`. The "Complex constants" docs row loses the `append` exception.
- **`K07` (Task 5.4):** the typechecker marks a range assignment's interface boxing on the `lhs` node (box kind, named type, static source) using the range's key/element type; `_emitRangeVar` wraps the value with the existing `_ifaceBoxWrap` / named-box helpers. Define forms (`:=`) are unaffected.
- **`K06` (Tasks 7.1–7.3):** each site converts an untyped constant to the complex struct with the existing untyped-literal-to-complex conversion in `src/backend/wasm/emit-exprs.js` (it needs the target wasm type, which these three sites do not pass): store through a pointer deref (assign and compound assign), the `switch` tag comparison (complex equality for the tag and each case, including complex-typed cases), and deferred call arguments (evaluated into the defer record with the parameter type as target).

- **`L05`, `L07`, `L08`, `L09` (Tasks 8.1–8.4):** deferred-call argument hoisting (`normalizeDeferStmt`, `src/lower/functions.js`) types each temp by the callee's declared parameter.
  - 8.1: an untyped constant or `nil` argument (a literal, a constant expression or a named constant) is not hoisted: it stays in the deferred call, where it takes the callee's parameter type as in a direct call, so no temp is declared with a defaulted type and the lowered code type-checks again on a second compile (`L07`, `L09`). Declaring the temp with a type node would need a type node for every parameter type (`spec.type` is read by the backends); leaving a constant in place needs none. Non-constant untyped values (`x == 1`) are still hoisted with their default type.
  - 8.2: with constants left in place, an inferred generic callee types them from its own signature (`L08`); no `monomorph.js` change.
  - 8.3: variadic arguments are typed by the variadic element type, and a spread argument (`f(s...)`) keeps `_spread` on its temp (declared with the slice type), so the call passes the slice through (`L05` JS/lowering).
  - 8.4: root cause pinned by probe: the lowered deferred wrapper lists its call under both `stmts` and `list`, so `desugarVariadics` (`src/backend/wasm/variadic.js`) packed the same call node twice (`[]int{[]int{…}}`, a `[[1 a]]` for `...any`, a spread wrapped again). `packCallArgs` marks a packed call (`_variadicPacked`) and skips it the second time; `emitDeferStmt` needs no change, and `defer fmt.Println("x", 1)` now prints (`L05` WASM).
- **`L01` (Task 9.1):** `_emitRangeAssignStore` takes the assignment target node, not a name: identifiers keep the current local/boxed/global paths; index (slice, array, map), selector and deref targets evaluate the target address once before the loop body iteration and store through the existing assignment-statement lvalue emitter, with the Task 4.1 interface boxing when the target type is an interface.
- **`L02` (Task 9.2):** the range-over-func assignment path records the same `_rangeBox` holder as Task 5.4 on each assigned `lhs` using the iterator's yield parameter types (`_checkRangeIterAssignVars`), and the JS iterator loop wraps the yielded value with `_ifaceBoxWrap` / the named-box helpers before assigning.
- **`L03` (Task 9.3):** the JS assertion / type-switch unboxing of a defined slice type returns `null` for a boxed nil slice (the same value the nil `any` held), like maps; pin the exact unwrap site at task start.
- **`L04` (Task 9.4):** arrays containing a type parameter in a generic function get the Task 6.4 treatment: JS fmt formatter and interface tag from the instantiated array type on every call, and the WASM monomorph names the instantiated array type. Docs: the `fmt` of a value in an `any` row lists arrays with maps and slices.
- **`L06` (Task 9.5):** `_genComplexBinary` evaluates each non-trivial operand once: `==`/`!=` become `__ceq(l, r)` / `!__ceq(l, r)` (a small helper taking two complex values) or bind the operands to temporaries when they are plain identifiers; arithmetic is unchanged.

- **`M01` (Tasks 10.1–10.2):** 10.1: the result of a comparison (`== != < <= > >=`) is an untyped bool, as are `&&`, `||` and `!` of untyped-bool operands; assignment to `bool` or any defined bool type works (`assertAssignable` with an untyped bool source), and it still defaults to `bool` for `:=`, interface boxing and `fmt`. Typed `bool` operands keep producing a typed `bool`. 10.2: `deferTempType` also returns the parameter's type for a non-constant untyped argument (comparison, shift) and the temp is declared with that type, using a type node that resolves the parameter's type (a `TypeName` of its declared name for package-level defined types and basic types), so the lowered code type-checks again on a second compile.
- **`M02` (Task 10.3):** the default type of an untyped rune constant is `rune` (`int32`): `r := 'x'` and `var a any = 'a'` get `int32`; `var i int = r` becomes the usual `Cannot assign` error. WASM boxing already handles `int32`. The change may flag Go-source stdlib or example code that mixed `rune` and `int`; fix such code in the same task and say so in the commit body.
- **`M04` (Task 11.1):** pin with a probe at task start: make the compile-time formatter and the `any` box for maps and arrays whose key or element is `bool` or an integer of at most 32 bits carry their type (JS fmt tag, WASM box/name), as Phase 6 did for slices and 64-bit integers; update the `fmt` row if it contradicts.
- **`M03`, `M05` (Tasks 11.2–11.3):** 11.2: the range-over-func assignment path records `_rangeBox` on index, selector, map-entry and deref targets (the Task 9.1 target model) and the JS iterator loop wraps the yielded value before the store. 11.3: a deref (`*p`), index or selector target of a range-over-func assignment resolves its sub-expressions as uses, like every other assignment target.

- **`N01` (Task 12.1):** in the binary-expression check, `&&` and `||` yield the operand type when both operands have the same type (typed or defined bool), the typed operand's type when the other is an untyped bool, and report `mismatched types` when two different typed bool types meet; two untyped bools stay untyped (Task 10.1).
- **`N02` (Tasks 12.2–12.3):** a shared integer-constant check (message like Go's: `invalid array length …`, `invalid argument: index … must be integer`, `… must be integer` for `make`) accepts an untyped constant representable as an `int` (`2.0`, `'a'`) and an integer-typed constant, and rejects bool, string, `nil`, non-integral float, complex and typed non-integer constants. 12.2 applies it in `_foldArrayLen` (array types, array literals, type declarations); 12.3 applies it to index expressions and the sizes of `make`.
- **`N05` (Task 12.4):** `_checkRangeIterAssignVars` calls `assertAssignable` with each yield parameter type against its target (identifier, index, selector, deref), with Go's `Cannot assign <T> to <U>` message; interface targets keep the Task 9.2/11.2 boxing marks.
- **`N03`, `N04` (Task 12.5 and 12.6 below):** N03: the func-valued map formatter path accepts the small key kinds (pin at task start). N04: in JS generic code the tag of a boxed map or array comes from the call's instantiation, not the first boxing (pin the mechanism at task start; wasm already monomorphises).
